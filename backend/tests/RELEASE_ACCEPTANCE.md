## 已修复与验收边界

- **同步**：相同自然身份换为规范主键时旧主键全部消失，守卫曾误报整表被清空。已用同名及无关项目对照验证，只放过可核实的重新编号。未配地址的手工同步现在即时返回失败原因，不再诱使 UI 轮询。清单消失必须中止且无远端写入；损坏/中断后重试保留两侧提交。覆盖恢复以用户选定备份为准，合并导入和覆盖恢复不是同一种“保留本地”。CSV 为导出回读，不存在 CSV 导入功能；ICS 走产品导入。
- **并发**：三条连接持有不同物理连接，同时启动任务编辑、定时作业认领和同步。每轮共 16 次编辑、16 次认领、16 次同步；故障点观测到一次 BUSY，测试按释放信号重试并核对无重复。另一组屏障测试强制规划期间改动，验证作废旧计划。终局两库业务行、完整性、外键与静稳零推送均核对；不宣称无限负载永不报锁。另有两个源码边车与回环 HTTP DAV 的十场景走通，非云端数据。
- **排期**：补下午明确空腹检查首轮问询；不替用户改期、不作诊断。规则可识别的自定义红线不再只靠模型；雨天之外增加日最大风速的户外避让；有不同峰谷证据时，高耗深度任务优先峰时，但不突破硬约束。
- **凭据与消息**：WebDAV 密码、模型和 Composio Key、渠道 Secret 及微信令牌不从对应配置响应回显。模型、同步编辑支持保留/替换/清除。仍不能据此认证任意自由文本、MCP env/headers 或历史归档没有秘密。消息入站以渠道与非空平台 ID 确定用户消息主键，唯一写入成功才驱动处理；重启可防重复，但认领后、完成业务前异常退出不保证补发；无平台 ID 时不能承诺去重。
- **失败留痕**：早期浏览器定位停在日程页而不是收件箱、JUnit 输出值写错均属测试工具问题。此前全库 1773 过/1 失败暴露 `/sync/run` 假成功；双端回环早期失败暴露恢复后的同步顺序和规范主键问题。这些结果没有用重试洗入正式三轮。
- **其他工具**：前端 `tsc --noEmit` 通过；宿主已有两项 Rust 单测通过。项目无可直接运行的 ESLint 脚本，不声称 lint 全绿。未重建 NSIS，浏览器录入持久化不等于真实 WebView、手机休眠或 SDK 端到端 SLA。

## 复跑

在项目根目录，使用 Clara 环境 Python。需要已安装的 Vite、Node、Playwright 与兼容 Chromium；非默认安装可设置 `CLARA_QA_PLAYWRIGHT`（Node 包路径）和 `CLARA_QA_BROWSER`（浏览器可执行文件路径）。每次选择不存在的输出目录：

```powershell
1..3 | ForEach-Object { python backend/tests/run_release_round.py ".pybuild/acceptance-new/r$_"; if ($LASTEXITCODE) { throw "第 $_ 轮失败" } }
python backend/tests/summarize_release.py .pybuild/acceptance-new/r1 .pybuild/acceptance-new/r2 .pybuild/acceptance-new/r3
```

每轮输出 `results.xml`、`pytest.log`、`startup.json`。本次在 `.pybuild/rc8/`，汇总 `summary.json`。原始本地证据不入版本库。真实用例在 `backend/` 下单独执行 `python -m pytest tests/test_qa_real_webdav.py -m real_webdav` 和 `python -m pytest tests/test_qa_real_llm.py -m real_llm`；开关和配置必须先安全注入，不能把密钥写进命令、报告或 Git；切勿用 `-l/--showlocals` 输出凭据。模型使用三轮共用额度账本，DAV 用 UUID 子目录及归属标记，禁止清空账号根目录。

按“有事实依据、用户知道下一步、针对当前任务”三个观察点复核上述合成样本。样本不是统计意义的准确率，也未证明所有提示词下零幻觉。完整脱敏结果留在 `.pybuild/live-release/`。

追加抽测：危机话术 22.42s、晨报 16.11s，硬契约 2/2。危机样本没有捏造任务 ID，主动说明真实合成日历为空，但同时出草案触发「应先给策略」软告警；此样本不是已填满日历的替代证据。晨报关联了两项输入任务并辨别时段已过，不冒称任务已执行。记忆例外在第二条消息触及 30 次累计请求上限，pytest 报 1 failed + 同一用例 teardown 1 error；不计两个失败样本，也不当作已证实的仲裁缺陷。全体真实模型抽测为 12 个场景实例，11 个完成并通过硬断言，1 个未完成；主抽样以外的真实模型场景未全部运行。已用 30/30 个供应商请求。

**真实坚果云：两轮完整通过，第三轮未通过。** R1 10/10（86.30s），R2 10/10（86.13s）。R3 首推通过，B 冷启动拉取报告失败；teardown GET 归属标记收到明确 HTTP 503，按设计拒绝删除。R3 实际 1 passed、1 failed、同一用例 1 teardown error（34.41s），后续 8 项未执行。三轮共 21 个成功的场景实例/计划 30 个，不能报 30/30。两轮完整通过均含：两个独立源码边车、真实云目录、增删改与冲突、恢复前故意偏离、重启逐行还原、多轮交替写入无追加重试。R3 可能是服务限流；没有证据确定第一次拉取失败的唯一原因，也没有证据表明原云数据丢失。前两轮专属目录已按标记清理，第三轮 `qa-test-bb1126e5f089435b80e5d03716386e52` 未确认清理；未清空原目录。仅在服务冷却后、验证所属标记时处理该目录，不以清空云盘修复 503。

## 放行建议

**源码候选可进入安装包验证，不建议现在正式发布。** 重跑真实 DAV 冷启动与完整第三轮（保留原始失败）；补真实模型有限会议例外在禁止窗内外的执行验证；在与源码匹配的 Windows 安装包上测安装、升级恢复、退出冲刷及启动时间。四渠道账号的手机最终投递、睡眠唤醒与 SDK 指数退避未真机验收。管理哲学未穷尽组合，尤其是会后缓冲、每日三要事与自定义红线三者同时生效。物理断电、长期磁盘增长和浏览器首个 AI 草案可见 P95 不在本轮证据范围。
